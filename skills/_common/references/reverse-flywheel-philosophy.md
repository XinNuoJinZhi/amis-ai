# 反向飞轮的产品哲学

amis-ai 不只是"用 AI 帮你写代码"。它有一个明确的**飞轮闭环**，理解它能让你避开所有"自由发挥"型的失败。

## 飞轮长什么样

```
   用户描述需求
        ↓
   生成 Amis JSON  ←──────────┐
        ↓                       │
   [反向：JSON → 代码]            │
        ↓                       │
   沙箱里 dev 启动              │
        ↓                       │
   用户预览、确认                │
        ↓                       │
   采纳 → code_sample 表          │
        ↓                       │
   下次类似需求 → RAG 检索 ─────┘
```

**关键**：你生成的代码不是一次性消费品，**它会被沉淀回知识库供下次复用**。所以代码质量直接决定飞轮转得好不好。

## 三层防线（你的工作守则）

### L1 · 事前约束：不要凭通用知识硬怼

你脑子里"标准 Vue 项目"或"标准 React 项目"的写法，**和这个项目的脚手架可能完全不一致**。例子：
- 通用 Vue3 项目可能用 Vuex / Pinia 做状态管理 → 本项目可能用 UniApp 自带的 reactive 模块
- 通用 React 项目可能用 react-router → 本项目可能用文件路由
- 通用项目可能用 axios → 本项目脚手架可能已经封装了 `useApi`

**永远先读当前栈 SKILL.md 里指定的 references，再写代码**。

### L2 · 事中纪律：不动底座

脚手架（scaffolds/{tech-stack}-template/）里有些文件**绝对不能动**：
- 入口文件（main.ts / main.tsx）
- 应用根组件（App.vue / App.tsx）的主题/i18n/全局拦截器注入
- 构建配置（vite.config.ts、webpack.config.js）
- 主题 token 文件
- 路由根（不是页面级路由配置，是路由根注册）

**为什么**：这些文件被改 = 飞轮里的"底座"被污染 = 下次复用时谁也不知道这份脚手架到底是什么状态了。

**要新增能力**：在 `src/pages/`、`src/api/`、`src/components/`、`src/utils/` 等业务目录里加文件。

**要改全局配置**：和用户确认后，**专门做一个 PR/issue**记录原因，**不要"顺手"改**。

### L3 · 事后反馈：错误是诊断证据

dev 启动失败、控制台 error、用户从 IDE 把日志塞进对话——这些都不是"用户的问题"，是你下一步行动的依据：

1. **第一时间读错误日志**——别请用户"再试一次"
2. **用 Read/Glob/Grep 工具定位代码**
3. **修代码、保存、明确告诉用户"已修复 X，请刷新预览"**
4. 修不动再说"我需要 Y 信息才能继续"

最常见的失败模式（按出现频率排序）：
- 漏写 `pages.json`（uniapp）/ 漏注册路由（react-router）
- 用错组件库前缀（用了 `<el-xxx>` 而不是当前栈要求的 `<wd-xxx>`）
- 在组件里直接 `axios.get` 而不是走 `src/api/` 模块
- 改了 main.ts / App.vue 的"底座"区域

## 采纳即沉淀

当用户点"采纳"按钮，你生成的代码 + 对应的 Amis JSON 会被**自动入库**到 `code_sample` 表。下次有相似需求，RAG 检索会把它当 Top-3 拼进新任务的 system_prompt。

**含义**：你今天偷懒写的烂代码，明天会被 AI 学会、后天会污染整个飞轮。
**所以**：每条代码都按"会被反复复用"的标准写。

## 一句话总结

> **你不是一个"按需生成代码的助手"，你是一个"沉淀可复用资产的工人"。**

这是 amis-ai 整套设计的本质区别。
