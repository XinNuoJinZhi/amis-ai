## 三、解读

### ✅ 双路召回价值显化（彻底突破上一轮的 0pp 困境）

第一轮：B 组 kw 命中 50%，但**召回源全是 baidu-amis**，看不到价值。
第二轮（入种子后）：B 组 kw 命中 **81%**，且 **7/8 task 召回到 zc-amis-builtin 种子**，A 组只有 5/8 召回。这次的对比让人**信服双路召回真的能拉开 source pool 差异**。

### ✅ 关键证据 — ZC 种子被 keyword 加分拉到 Top-3

A 组 task 332-339（纯向量）：5 个 task 召回到 zc-amis-builtin（说明种子的 amis_json_summary 与 prompts 的描述也有语义相关性）。
B 组 task 340-347（双路）：7 个 task 召回到 zc-amis-builtin（多了 2 个：rs5 和 rs7）。

数据级证据：
- rs2 BI 看板：A 组虽召回 zc-amis-builtin 但 kw=0（向量召回到的不是 934 而是其他 zc-amis 池），B 组 kw=5（934 被双路加分顶进 Top-3）
- rs3/4/6 B 组 kw_sum=9-11，多个种子样本同时被 boost

### ✅ 页通过率上升（出人意料）

通常增加 RAG 样本会让 prompt 更长、LLM 生成更复杂，**但 v2 的 B 组页通过反而比 A 组高 4.2pp**。可能因为：
- ZC 种子的 `full_code` 直接给了 React+antd 适配 ZC schema 的代码模式（如 modeltable→Table+TreeSelect 翻译），LLM 学了之后生成更稳定
- A 组只有 baidu-amis 的纯 amis 样例，少了"业务代码"参考

### ⚠️ 异常项

1. **B 组 rs1 无 RAG event**：可能命中 backend create_task 的某个早退路径（如 only_approved_count=0 缓存命中）。需排查 [agent/src/services/rag.py:32-49](../../agent/src/services/rag.py) 的 TTL 缓存逻辑。
2. **A 组 rs1/3/5/8 退化 2/3 pass**：上一轮 A 组 100% 通过。可能：
   - 召回到 zc-amis-builtin 种子的 full_code（React+antd）让 LLM 学到不熟悉的模式
   - 或 LLM 偶发抖动
3. **rs7 双路反而退化** (3/3 → 2/3)：B 组召回 zc-amis-builtin 之后某 page 失败。详查需看 task 346 的 page log。
