## 三、解读 — 一项胜，一项败

### ✅ 胜利：双路召回机制本身有效

A 组（关闭双路）→ keyword 加分 = 0；B 组（开启）→ 50% 样本有 keyword 加分，平均 0.79 kw/sample。证明 1.4 B.1 / 1.5 W4 修的双路召回 SQL 路径（cardinal intersect + 0.06×n boost）**真的在生效**，没有静默失效。

### ❌ 失败：召回敏感设计漏洞 — 没拉到 zc-amis 样本

预期 B 组应**召回到 zc-amis 样本**（来自 zc-web-1.3 评测时入库的 133 个 zc-editor-web stack 样本），但 24 / 24 全是 baidu-amis。诊断：

**根因 1：tech_stack 硬过滤**
search_code_samples 用 `tech_stack=react-antd-vite` 做硬过滤（[rag.py:315](../../agent/src/services/rag.py)）：
```sql
"AND ($6::text IS NULL OR tech_stack = $6)"
```
zc-amis 样本 tech_stack 全部是 `zc-editor-web` → 直接被踢出召回候选池，跟 keyword 命中没关系。

**根因 2：zc-amis 样本的 keyword_index 没有 ZC 特征关键字**
查 zc-amis 样本（id=592-724，133 条）的 keyword_index：
```
{api-path:api/mock2, type:chart, type:divider, type:input-email, ...}
{type:form, type:input-file, type:pdf-viewer}
{api-path:api/crud, type:crud}
```
全是标准 amis 组件（chart/form/crud/input-*），**没有 modeltable / report-forms / dynamic-form / flowCreate 这种 ZC 二开关键字**。这是 zc-web-1.3 当时入库的方式：把 baidu-amis 文档样例镜像过来当 ZC web 种子，所以本质就是 baidu-amis 内容 + 改 tech_stack 标签。

### 结果

B 组的 12 个 kw 命中**全都是 baidu-amis 里的标准 amis 组件**（form/crud/table）keyword 被 boost 进 Top-3，与 ZC 二开毫无关系。LLM 拿到的两组样本本质一致 → 生成代码一样 → 24/24 都过。

## 四、Lessons learned — B 项再做一遍要改的事

1. **tech_stack 维度对齐**：召回敏感对照必须用**同一 tech_stack**。要么两组都跑 `react-antd-vite`（用 baidu-amis 池）、要么都跑 `zc-editor-web`（用 zc-amis 池）。混跑跨 stack 没意义。

2. **种子样本要带 ZC 特征 keyword**：当前 zc-amis 池没有 modeltable / report-forms / flowCreate 这种 ZC 二开特征。如果想验证「ZC 模板 vs 普通 antd」差异，需要：
   - 手工入库 5-10 条「真 ZC 模板代码」样本（含 modeltable 等组件）
   - 入库时 keyword_index 自动从 amis_json 提（已经支持）
   - 让 prompts amis 含这些组件 → kw 命中后拉到 ZC 样本

3. **page-level 召回敏感更刁钻**：r4_baseline 是 task-level RAG 注入（每 task 仅 1 次 rag_samples_injected）。如果想看每 page 召回差异，应该跑 r1_skeleton / r2_prompt / r3_refactor 之一（page-level reuse 策略）。

4. **页通过率不是召回敏感指标**：1.5 W4 已发现 100% pass 时两组无差异；1.6 W2 也复现。**真正可信指标是「召回源差异」**（zc-amis vs baidu-amis）+ keyword_hits 分布，而非端到端 pass 率。

## 六、结论

**1.6 W2 baseline 0 结论**：
- ✅ 双路召回 SQL 机制经实证仍在生效（B 组 50% 命中、avg 0.79 kw/sample）
- ❌ 召回敏感 prompts 设计不到位，未能拉开两组的 source_team 差异
- 🟡 24/24 pass 两组同结果是预期内的（页通过率不是该评测的指标）
- 📋 1.6 W2 续：种子真 ZC 模板样本 + runner CSV 加列 + prompts 二次设计

> 💡 **真正的洞察**：1.5 W4 修的 dual_route 路径确实工作，1.4 B.1 设计是对的。但**召回敏感的评测要让评测集自带"被 keyword 拉开的目标样本对"**，而不是寄希望于现成样本池里有这种对子。当前样本池是镜像 baidu-amis docs，缺少 ZC 特征。
