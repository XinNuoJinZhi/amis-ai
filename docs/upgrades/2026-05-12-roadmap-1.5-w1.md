## 一、W1.1 · 分类器偶发空 category 修复

**问题来源**（1.4 W4 收尾 #3）：task 258/259/238 三例 `category=__other__`，原因是 LLM 调用偶发 ≥3s → backend timeout 3s 阻断 → 退化为 `(None, None)` → 路由偏置失效。

**改造**（commits 待 W1 收尾批量提）：

| 文件 | 改动 | 效果 |
|---|---|---|
| `backend/src/handlers/project_generation.rs:237` | timeout 3s → **5s** | 给 fast 模型 + 慢启动多 2s 缓冲，足够覆盖 P95 |
| `agent/src/routers/internal.py` classify endpoint | 加 **单次内部重试** + **未知 category 视作软失败**触发重试 + 2 次都失败时 fallback `__other__`/0 + 返回 `fallback_reason` 字段 | 永远不让 backend 拿到 5xx；可观测降级原因 |

### 设计要点

1. **重试上限 1 次**（共 2 次尝试）：fast 模型 P95 < 2s，2 次 ≤4s 仍在 backend 5s 内
2. **未知 category 也算软失败**：LLM 偶发输出 `工单管理` / `多页面` 这类自由文本时，重试一次让它修正；2 次都不行才降级
3. **降级不返回 ok=false**：返回 `{ok: true, category: "__other__", confidence: 0.0, fallback_reason: "..."}` — backend 拿到 `__other__`/0 时 llm_selector 自动退化为纯 score 决策，与"分类器没接通"时行为一致
4. **可观测**：`fallback_reason` 字段写入 backend 日志，方便后续统计降级率

### 验证

- `cargo check`（backend/）✅ 编译通过
- `python3 -c "import ast; ast.parse(...)"` ✅ Python AST 合法
- 集成验证：W4 跑评测时观察 `category=__other__` 比例（1.4 W4 实测约 5%，目标 < 2%）

## 三、W3 骨架 · A/B 分桶 DB schema（消费侧未开）

**为什么先做骨架**：B 项 A/B 框架完整需要 W2（estimate 公式校准 + 数据可信）前置，但 schema + 写入逻辑可以提前落，等 W2 数据来了切消费侧即可秒上线，不再做 schema migration。

**改动**：

| 文件 | 改动 |
|---|---|
| `backend/src/main.rs` migration | `ALTER TABLE project_generation_task ADD COLUMN IF NOT EXISTS ab_variant VARCHAR(16)` + `idx_pgt_ab_variant` 索引 |
| `backend/src/entity/project_generation_task.rs` | 加 `ab_variant: Option<String>` 字段 |
| `backend/src/handlers/project_generation.rs` | `compute_ab_variant(user_id)` helper（**骨架阶段统一返回 None**）+ `task_record.ab_variant: Set(compute_ab_variant(user.id))` |

**为何骨架阶段返回 None**：

- W2 数据未到位，B/A 哪边公式更好还不知道，开 A/B 等于盲投
- W3 完整实现需要：(a) settings.llm.routing.ab_test_enabled 开关；(b) `category_tier_overrides_json` 按 variant 切两套；(c) admin endpoint `/api/admin/ab-compare`；(d) dashboard 三轴图
- 现在写 None 让任务正常跑，等 W3 真做时只改 `compute_ab_variant` 函数体即可，其他都已就位

**消费侧设计草稿**（W3 完整工作时落）：

```rust
fn compute_ab_variant(user_id: i32) -> Option<String> {
    if !read_ab_enabled() { return None; }
    let bucket = (user_id as u32).wrapping_mul(31) % 100;
    Some(if bucket < 50 { "a".into() } else { "b".into() })
}
```

llm_selector 入参加 `variant`，读 `llm.routing.category_tier_overrides_json_a` / `..._b` 两套配置。
admin endpoint：`SELECT ab_variant, AVG(actual_cost_tokens), AVG(成功率), AVG(耗时) FROM project_generation_task WHERE ab_variant IS NOT NULL GROUP BY ab_variant`。

**验证**：`cargo check` ✅ 编译通过；migration 幂等（IF NOT EXISTS），重启 backend 自动建列 + 索引。

## 四、W1.2 降级说明（actual_cost_tokens 重复累加）

**调研结果**：1.4 W4 #4 描述「retry 任务上重复累加 / 加 retry_count 维度 / reset = 0」与当前实现对不齐。

- **single-page 路径**：`spawn_dev_status_watcher` 在 dev_start 失败时 `fix_attempts++`，但 `project_events.rs::persist_event` **没接 actual_cost_tokens 累加**。
- **multipage 路径**：`multipage_session_watcher::persist_event` 在 `llm_call_snapshot` 事件累加，但 `multipage_scheduler` **没 fix_attempts++ 概念**（page 失败 → page status=failed）。

→ 当前实现下根本不存在"retry 累加同一 task"路径。接力文档 #4 描述的真实问题可能是：
- **WS 重连导致同一 `llm_call_snapshot` event 被重推累加**
- **或 multipage 评测中观察到的"page A 失败后 LLM 用 N token 重写 page A，加到 task 总和"** —— 这其实是正确行为

**决策**：W1.2 **降级到 1.5 后期**，等真实生产数据复现到具体路径后再动。盲目 reset 反而破坏成本审计真实性。
