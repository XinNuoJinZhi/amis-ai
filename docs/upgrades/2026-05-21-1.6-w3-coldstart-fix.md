## 一、本轮始末

接力时发现 5-13 evening baseline 的「分类器 7d null+other 占比 54%」未收敛，今天循着排查走出了一个**多年技术债**：1.4 W1 / 1.5 W1.1 一直在改"LLM 偶发慢"，但每次 backend restart 后第一批业务任务全栽 NULL 的真因是 **agent FastAPI 冷启动 3s 窗口**。

期间还顺手发现 8080 被 worksy-backend 误占的乌龙，由此引出全栈健康身份探测。

### C. start-services.sh status 加身份探测（fa459a4）

每个端口 UP 时再调 health endpoint 验证 service 字段：

| port | 探测 URL | 期望 service |
|---|---|---|
| 8080 | `/api/health` | `amis-ai-backend` |
| 8090 | `/health` | `claw-agent-server` |
| 8091 | `/health` | `sandbox-service` |
| 8000 | `/health` | `amis-ai-agent` |

任一端口被别的进程占用时，提示 `⚠️ PORT 被【<other_service>】占用，非 <expected>！`

### D. start-services.sh start 末尾 wait_for_health（fa459a4 + 54cb06b）

```bash
wait_for_health "sandbox"    "http://localhost:8091/health"    "sandbox-service"
wait_for_health "claw-agent" "http://localhost:8090/health"    "claw-agent-server"
wait_for_health "backend"    "http://localhost:8080/api/health" "amis-ai-backend"
wait_for_health "agent"      "http://localhost:8000/health"     "amis-ai-agent"
```

`wait_for_health` 每秒 poll 一次，最多 30s，返回正确 service 字段才算 ready。

## 五、留下的思考

1. **agent FastAPI lifespan 这 3s 是否可压缩？** 看 lifespan hook 在做什么（embedding model warm-up？pgvector 探测？）— 1.6 W4 可选优化
2. **claw-agent / sandbox 0s 是真的还是探测太粗？** 它们 Rust axum 几乎是 socket listen 就 ready，3s 探测周期下显示 0s 合理
3. **能否给 start_one 加 per-service health hook 而不是 start_all 末尾统一等？** 这样 backend 启动后立即可以等 agent，比 sleep 2 + 末尾批量等更精细 — 但当前 0s 0s 0s 3s 已经够好，不动
