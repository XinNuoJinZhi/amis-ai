## 一、A 轨 · W2 estimate 公式校准

### 痛点

1.4 W4 实测 task 260：`estimated=1785` vs `actual=409,828`（差 230×），原因是粗估公式只算「单次 LLM 调用 input + output」，没考虑 Agent 多轮调用时整个 system prompt + 历史 + Skills + RAG 每轮都重新发送。

### 改动

| 文件 | 内容 |
|---|---|
| [backend/src/services/quota.rs](../../backend/src/services/quota.rs) | 加 `estimate_task_cost_calibrated` async 版本：优先查 category 历史中位数（≥10 样本），fallback 公式 × 校准系数 200 |
| [backend/src/main.rs](../../backend/src/main.rs) | 加 2 个 settings：`llm.quota.estimate_calibration_factor`（默认 200）/ `llm.quota.estimate_min_samples`（默认 10） |
| [backend/src/handlers/project_generation.rs](../../backend/src/handlers/project_generation.rs) | create_task 调用从 sync `estimate_task_cost` 换成 async `estimate_task_cost_calibrated` |

### 决策树

```
estimate_task_cost_calibrated(state, amis, extra, complexity, category) :=
    if category != Some(__other__) and category 历史样本 >= min_samples (默认 10) :
        median(accumulated_cost_tokens of recent 30d) × clamp(complexity/20, 0.5, 2.5)
    else :
        raw_formula × calibration_factor (默认 200)
```

### 调优路径

- 上线后跑一段时间，admin 看 `actual_cost_tokens` / `accumulated_cost_tokens` 真实分布
- 各 category 收集 ≥10 样本后自动走中位数路径
- 系数 200 是 1.4 W4 单点实测推断，若上线后偏差大可调
- 极端 complexity 任务用 `clamp(0.5, 2.5)` 防过度缩放，避免极简任务被估 ×0 或极复杂任务被估 ×5

### 验证

- `cargo check` ✅
- 历史中位数查询用 `percentile_cont(0.5) WITHIN GROUP` PostgreSQL 原生函数（pgvector image 已自带）
- 老 sync `estimate_task_cost` 保留，方便单元测试和无 DB 环境的回归

   ```json
   {"static_page":"fast","oa_form":"strong","ecommerce":"frontier"}
   ```
2. **开总闸**：`llm.routing.ab_test_enabled = true`
3. 任务自动按 `user_id × 31 % 100` 稳定分桶，写入 `ab_variant`
4. 1-2 周后 `GET /api/admin/ab-compare?days=14`，比对两桶 cost-per-success
5. 选优胜配置覆盖 `_json`（A 组默认），关 ab_test_enabled

### admin endpoint 输出格式

```json
{
  "window_days": 7,
  "buckets": [
    {
      "variant": "a",
      "total": 120, "succeeded": 108, "success_rate": 0.9,
      "avg_actual_cost": 35000.0,
      "avg_accumulated_cost": 78000.0,
      "avg_estimated_cost": 405000.0,
      "avg_duration_sec": 420.0,
      "avg_fix_attempts": 0.8,
      "cost_per_success_k": 86.6
    },
    { "variant": "b", "...": "..." }
  ]
}
```

`cost_per_success_k` = `avg_accumulated_cost / success_rate / 1000`，越低越好（每个成功 task 平均消耗 k token）。

### W4 实测结果（3 轮共 6 次评测）

详见 [eval/1.5-rag-stress/SUMMARY.md](../../eval/1.5-rag-stress/SUMMARY.md)。

**🐛 关键 bug 发现 & 修复**：1.4 B.1 双路在多页路径下**从未真正工作过**。
- 根因：[project_generation.rs:432](../../backend/src/handlers/project_generation.rs#L432) 调 `fetch_rag_extra_sections` 时传 `payload.amis_json`，但多页任务该字段是空 `{}`（真 amis 在 `payload.pages[]`）
- Fix：改传 `amis_for_analysis`（多页合并后的整体 JSON）
- 影响：1.2 多页 / 1.3 ZC Web / 1.4 评测**所有多页任务**的 B.1 keyword 召回长期等于纯向量

**B3 vs A3（修复后的真对照）**：

| 指标 | B3 (dual ON) | A3 (dual OFF) |
|---|---|---|
| 任务成功率 / 页通过率 | 9/9 / 27/27 = 100% | 9/9 / 27/27 = 100% |
| **keyword_hits 总和** | **33 hits / 9 task** | **0 hits / 9 task** |
| 平均 cos similarity | 0.36 | 0.39 |
| 平均综合 score（sim + boost） | **0.534** | 0.486 |

→ B.1 实际"换样本组合"（用 kw 命中样本替代纯 sim 高的），不是"拉成功率"（已经天花板）。

### W1.2 · actual_cost_tokens 重复累加（升级到双列设计）

| 文件 | 改动 |
|---|---|
| [backend/src/main.rs](../../backend/src/main.rs) migration | 加 `accumulated_cost_tokens INT` 列 |
| [backend/src/entity/project_generation_task.rs](../../backend/src/entity/project_generation_task.rs) | 加 `accumulated_cost_tokens: Option<i32>` |
| [backend/src/services/multipage_session_watcher.rs](../../backend/src/services/multipage_session_watcher.rs) | watcher 同时累加两列，单 SQL 保事务一致 |
| [backend/src/handlers/project_generation.rs](../../backend/src/handlers/project_generation.rs) fix retry 触发点 | runtime-error fix（line 1172）+ dev_failed fix（line 1285）reset `actual_cost_tokens = 0` |

**字段语义**：
- `actual_cost_tokens` → **当前 attempt** 成本（fix retry 时 reset 0）
- `accumulated_cost_tokens` → **全部 attempt 累计**（永不 reset，审计用）

这样既符合接力文档"retry reset"诉求，又不丢失成本审计真实性。
