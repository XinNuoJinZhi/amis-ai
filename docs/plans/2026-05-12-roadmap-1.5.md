## 二、1.5 候选方向（6 选 2-3 排序）

### A. **estimate_task_cost 公式校准**（Quick win）
**痛点**：1.4 A.3 estimate 公式偏低 200×（实测 task 260 estimated=1785 vs actual=409,828），quota 系统形同虚设。
**方向**：
- 用 actual_cost 数据回归校准 estimate 公式（线性回归 / 经验加权）
- 把 `complexity_score × 50 + amis_len/3 + 500` 重写为 `f(complexity, page_count, history_avg_per_category)`
- 引入 category 维度估算：oa_form / zc_business 历史平均 cost × page_count
**估时**：1 周
**前置依赖**：积累 1 周以上 actual_cost 数据（约 50-200 任务）

### B. **A.4 A/B 框架**（数据驱动路由决策）
**痛点**：1.4 A.2 category × tier 偏置上线了但没有对照组验证收益。
**方向**：
- DB 加 `ab_variant VARCHAR(16)` 列到 project_generation_task
- 创建 task 时按 `user_id hash % 100` 分桶 variant_a / variant_b
- 两组 variant 走不同 `llm.routing.category_tier_overrides_json` 配置
- 加 admin endpoint `GET /api/admin/ab-compare` 返回两组 cost-per-success 对比
- dashboard 出图（页通过率 / 平均 actual_cost / 平均耗时 三轴）
**估时**：1-2 周
**前置依赖**：A 公式校准（actual_cost 数据可信）

### C. **page-bad 自动回流为 negative sample**（飞轮闭环最后一公里）
**痛点**：B.3b 评测显示 6 个 page 被评 bad，但只回填到 page_quality_verdict，没自动入 code_samples 作反面教材。
**方向**：
- spawn_judge_for_page 在 verdict=bad 时检测 `rag.judge.auto_page_negative=true`
- 自动 INSERT 一条 code_sample：is_negative=true / negative_kind='structural' / source_task_id=task / 提取该 page 的 amis_json 作 full_amis_json
- 触发 keyword_extractor 提关键字 + embedding 入库
- search_negative_samples 后续可召回这些"页级反例"
**估时**：3-5 天
**前置依赖**：B.3b 已就位，新增"bad page 应该入库"的人审样本观察（避免 LLM 误判扩散为负例污染）

### D. **更刁钻评测集**（让 B.1 双路效果可见）
**痛点**：1.4 B.4 评测三组都 100% 通过，没法判断 B.1 keyword 双路召回的真实价值。
**方向**：
- 设计 **对抗样本**：用户描述 vs amis_json 故意不一致（"请做用户管理" + 一个商品 amis JSON）
- 设计 **混淆样本**：含相同 type 但不同 ui_lib（ui-antd select vs ui-wot select vs zc user-select）
- 设计 **冷启动样本**：完全新业务类别（如医疗记录、教育课程表），RAG 召回信号弱时双路融合效果显著
- 跑 baseline / B.1 only 对比，记录 keyword_hits 命中率分布
**估时**：1 周（含人工设计 prompts + 跑评测 + 分析）
**前置依赖**：无

### E. **桌面端模板**（Tauri + Vue3，扩平台覆盖）
**痛点**：1.4 已有 Web + Mobile（H5）+ 小程序，但客户偶尔要 PC 客户端。
**方向**：
- `scaffolds/tauri-vue3-template/` + `amis-ai-sandbox:tauri-rust-node20` 镜像
- 主进程 Rust，渲染进程复用 Vue3 + Element Plus（1.4 落地的）
- skill 桶：`platform-desktop` + `stack-tauri`
- 评测加桌面侧菜单 / 多窗口 / 文件对话 等场景
**估时**：3-4 周
**前置依赖**：C（如果选 Vue3 渲染层）

### F. **Skills Marketplace MVP**（外部团队按标准协议接入）
**痛点**：1.2 引入了 `SKILLS_PLUGIN_PATHS`，但只支持挂载本地目录，无包管理 / 版本 / 发现。
**方向**：
- 定义 skill 包格式（tarball + manifest.json 含版本 / 兼容性 / 作者）
- 加 `/api/skills/marketplace` 列已发布包 + 安装命令
- 私有 nexus / S3 兼容存储 + 包签名校验
- RBAC：组织内私有桶 vs 公开桶
**估时**：4 周
**前置依赖**：1.3 Skills 标准协议（已有）

## 三、推荐路径

**最高 ROI 顺序**：

1. **A（estimate 公式校准）** — 1 周，让 quota 系统真正可用，前置 B 的成本对比
2. **B（A.4 A/B 框架）** — 1-2 周，把 1.4 A.2 路由决策从"猜"变成"看数据"
3. **D（更刁钻评测集）** — 1 周，让 B.1 双路价值可观察，决定是否值得升级到严格 RRF

**1.5.0 scope 建议**：**A + B + D** 三轨，总估时 3-4 周。

**1.6 候选**：C（page-bad 入库，等更多数据决定）+ E（桌面端，大工程）。
**1.7 候选**：F（Marketplace，4 周独立项目）。

## 四、跨版本风险

| 风险 | 应对 |
|---|---|
| actual_cost 数据样本少（1.4 才接通，task < 10）→ A 公式拟合不准 | 1.5 启动时先跑 50-100 个真实 task 积累数据再校准 |
| A.2 路由偏置改 estimate 后会重新影响 LLM 选型 → 任务行为变化 | 走 A/B 灰度（B 项），让用户感知不到行为突变 |
| 更刁钻评测集（D）可能暴露 B.1 单路 + bonus 在对抗样本下失效 → 需要升 RRF | 评测出问题再决定升级路径，参考 memory `b1_keyword_design.md` |
| page-bad 自动入库（C）可能引入低质 negative samples 污染召回 | 加阈值（confidence ≥ 0.85）+ admin 抽审，不全自动 |

---

## 五、不做的事

1. **不做 mobile-native**（React Native / Flutter）—— 当前 H5 + 小程序覆盖足够
2. **不做 LLM-as-judge 全自动 + 无人评测** —— 1.3+1.4 评测显示 LLM 评委对 ZC 二开组件 schema 仍需人审兜底
3. **不做 multi-tenant SaaS 化** —— 仍是 self-hosted 工具定位，组织级权限到 1.7.F 即可
4. **不主动改 estimate 公式而不灰度** —— 直接换公式可能让 quota 突然全员超额，必须 A/B 验证
