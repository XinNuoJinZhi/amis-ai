## ✅ 缺陷修复完成（2026-05-08 session）

### ✅ 缺陷 1：「session 真完成」等待逻辑已加

**新模块** [`backend/src/services/multipage_session_watcher.rs`](../../backend/src/services/multipage_session_watcher.rs)：
- 订阅 `ws://{claw_agent_url}/tasks/{session_id}/events`
- 把每条事件以原文 JSON 落库到 `project_task_event`（关联 backend 的 multipage task_id），让前端 history REST 可回放每页 session 内细节
- 同时按 tracelog 配置归档（与单页路径一致）
- 看到 `status_change=succeeded/failed/stopped` 才返回；30 分钟超时兜底

**接入点**（5 处）：
- `run_unified` 后等 → 真完成才标 5 页 done
- `run_skeleton_stage` 后等 → 骨架真生成才让阶段 2 各页并发（不再扫到空骨架）
- `run_cleanup_stage` 后等 → cleanup 真完成才记 cleanup_done
- `run_r3_refactor` 后等 → 重构真完成才记 refactor_done
- `run_isolated_pages_with_shared_context` joinset 内每页 spawn 后等 → 不再 64ms 假完成

### ✅ 缺陷 4：闭环连线已加

**新增** `multipage_scheduler::run_epilog`（dispatch 末尾自动调用）：
1. 用 [`backend/src/services/multipage_reuse.rs`](../../backend/src/services/multipage_reuse.rs)（不依赖 regex 的纯 str 扫描，与 sandbox/src/reuse_metrics.rs 行为对齐）算 shared/ 复用率
2. 写一条 `reuse_metric` event（带 import_count / file_count / reuse_rate / strategy 四元组）
3. 成功任务才调 agent `POST /multipage/record` 写 RAG（status=pending 等人审）；失败任务跳过避免脏样本
4. 写 `rag_recorded` 或 `rag_record_failed` event 留痕

**新增** `AppState.agent_url` 字段（env `AGENT_URL`，默认 `http://localhost:8000`）。

**4 个单元测试** 在 `backend/src/services/multipage_reuse.rs` 全绿：zero / shared imports / dir missing / two-layer depth。

## 2026-05-09 session 后续修的隐性 bug（已在 dev/1.2.0）

接力文档原本说 4 项缺陷修了，e2e 跑出来又暴露 2 个：

| Commit | 说明 |
|---|---|
| `5c79140` | start-services.sh 启动子进程时清代理 env（脚本注释承诺过但实际只清了 build 阶段；导致 claw-agent-server 带 Clash 代理 502） |
| `4788c0a` | claw-agent-server `single_shot` 模式 + multipage scheduler 5 处传 `Some(true)` + dispatch 末尾回写 task 主表 status（之前漏了，task 永远 running） |

`single_shot` bug 真因：claw-agent-server task_loop 第 552 行 `while let Some(msg) = msg_rx.blocking_recv()` 设计假设是"前端 IDE 聊天等 follow-up"，多页 single shot 用法卡在这等不来 follow-up，永远不发 `status_change=succeeded`。`single_shot=true` 让它跑完 initial turn 直接 break。
